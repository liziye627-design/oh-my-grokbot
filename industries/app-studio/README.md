# App Studio 原生数字开发团队

`oh-my-app-studio@0.1.0` 将现有 Core Skills 组织为产品分析师、架构师、开发工程师、独立 QA 和审阅者五个原生角色。三个工作流分别支持功能开发、已有仓库故障修复、发布准备。没有新增模型调用循环，也没有安装上游框架或执行真实部署。

`industry.json` 是机器可读清单；`prompts/` 提供可交给原生 Bot 的角色提示；`fixtures/requests.json` 包含三条可替换为真实仓库的样例输入。`USER_PROVIDED_LOCAL_CHECKOUT` 必须替换成用户授权、可读取的实际工作区。样例不是已完成任务，测试模板保持 `not_run`，禁止当作测试结果提交。

## 激活与账号边界

通过共享行业包加载器校验清单、安装依赖的 Core Skills 并生成 Gateway 任务请求。原生应用中逐个创建或配置五个角色，绑定清单指定 Skills，人工交接任务。原生 Bot 创建 API、自动触发、原生 Result MCP 绑定和跨角色交接仍须真实账号验收；仅暂存清单不代表员工已经上线。Gateway 租户权限也不隔离同账号下原生 Bot 共用的云电脑。

仅将当前角色、当前步骤、必要上游证据、授权路径和任务标识交给执行者。Result MCP 凭证通过私密配置提供；审批与独立验收凭证不得交给执行 Bot。

## 验收操作

1. 选择 `fixtures/requests.json` 中一个请求，填入真实仓库与允许修改范围。记录初始工作区状态，保留他人变更。功能案例须预先确认过滤空列表、正常状态、清除过滤的三个结果；故障案例须先真实重现同名任务误更新问题。
2. 按清单 DAG 交接：上游文件存在且验收条件满足后才能启动下游。每一步的 `requiredArtifacts` 是本步需要产出的成果。依赖步骤失败时暂停该支路并报告具体缺项；修复后重跑受影响验收，不伪造自动恢复。
3. QA 在该仓库实际可用的测试命令和使用入口执行检查。`test-results.json` 至少包含运行环境、每项命令、退出码、期望与实际结果、证据位置；Web UI 保存浏览器验证证据，API 保存请求及脱敏响应。命令无法执行时状态为 `not_run`，整个任务不能宣称通过。
4. 独立 reviewer 检查补丁可应用、产物可打开、需求到测试的映射完整。对缺陷给出路径和可复现条件。通过前，所有阻塞项必须处理；上传文本产物到 Gateway 后，由独立 operator/verifier 决定验收。
5. 发布准备额外检查 `release-manifest.json` 的每个本地产物 SHA256、版本和构建命令；`approval-request.json` 至少包含 operation、destination、version、artifactSha256、expiresAt、rollbackPlan 和未验证项。可按 Gateway 当前批准请求协议将这些内容装入 payload，批准必须绑定精确哈希。此流程到“可审批发布包”结束，外部推送、合并、发布和部署须另有明确授权及可用执行通道。

预期故障验收：没有仓库路径应被标为输入不完整；测试失败不得继续发布；实现者不能验收自身成果；目标或产物变化使旧审批失效；没有真实账号只能标记 native activation pending。每次交付 `delivery.md` 应列出已实现内容、实际验证、失败和未验证项、产物索引及下一位负责人。

## 上游参考与适配取舍

2026-10-15 已打开核对以下官方 GitHub 项目；仅参考其公开设计思路，没有复制、下载或安装其代码：

- [GitHub Spec Kit](https://github.com/github/spec-kit)：需求和规格驱动工作流参考。本包采用明确的规格、计划、实现产物交接，保留本项目已有角色与 Gateway 协议。
- [Microsoft Playwright](https://github.com/microsoft/playwright)：浏览器真实端到端验证参考。仓库已有该工具时优先使用其真实页面验证和失败追踪；此包不自行安装浏览器或添加工具依赖，也不将截图单独当成功证据。

这些是参考项目，不是行业包新增能力依赖。实际使用前按目标仓库锁定版本、许可和安装政策处理。当前清单只引用已存在 Core 能力。
